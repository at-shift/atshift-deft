# atshift DEFT 試作版の導入・利用手順

DEFT は **Delegate Execution. Focus on Thinking.** の略です。
0.7.1 のプラグインslugは `atshift-deft` です。審査用候補版のため、まず独立したテストサイトで試してください。

### 旧 Structured Fields Prototype からの移行

1. テストサイトをバックアップします。
2. プラグイン一覧で旧 **Structured Fields Prototype** を停止します。データは削除しません。
3. `atshift-deft-0.7.0.zip` をインストールし、**atshift DEFT** を有効化します。
4. 保存済み記事・部品・接続・予約を確認します。旧版と新版は同時に有効化しません。

slugが変わるため、旧版への上書き更新ではありません。旧版は停止したまま残せます。
内部の保存名・権限名・接続URLは引き継ぎます。MCP endpoint、OAuth issuer、
`page=structured-fields` を手作業で `atshift-deft` に置き換えないでください。

対象: **0.7.1 審査用候補版** / 2026-11-01

0.7.1では下書きのごみ箱・復元、所有者表示、投稿先一覧への非公開予約記事の表示を追加しました。以下のGitHubリンクは公開済み0.7.0のままです。0.7.1を検証するときは別途提供された候補版ZIPを使用してください。既存ReleaseのZIPは差し替えていません。

0.7.0では投稿先・既存カテゴリー/タグの選択と、公開内容だけの構造JSON・JSON-LD出力に対応しました。更新後はDEFTからAI用手順書をダウンロードし直し、AIに読ませてください。以前ダウンロードしたファイルは自動更新されません。

0.5.xからは一度だけZIPで上書き更新してください。0.6.0以降のGitHub配布版は、今後の正式なGitHub ReleaseをWordPressのプラグイン更新画面で受け取れます。自動更新の有効・無効はWordPress側の設定に従います。WordPress.org申請版にはGitHub更新機構を含めず、同じバージョンの翻訳ファイルを両方に同梱します。申請は審査完了・公開を意味しません。

この版は検証用です。本番サイトではなく、バックアップを取得した独立したテストサイトで試してください。
既存の atshift Fields / CFS を置き換えるプラグインではありません。既存投稿の移行も行いません。

## 1. 現在できること

- 普段使うAIへ、利用できる部品・項目・作成ルールをJSONで渡す。
- AIが作った記事JSONを取り込み、本人専用の下書きとして保存する。
- WordPressの実テーマでプレビューし、必要なら一部を手動修正する。
- 全体カタログの部品を再利用し、本当に足りない構造だけ共通登録する。
- 同じQ&Aを一覧表示・開閉表示に切り替える。
- 画像・PDFを非公開で預かり、記事に紐付け、保存版ごとに確認する。
- 対応するMCPクライアントから、本人の下書きを直接保存・再開する。
- 不要な下書きをゴミ箱へ移動し、必要になったら復元する。
- 公開権限を付けた接続では、担当者の希望する即時公開・予約日時をAIが設定する。

**初回の接続設定は必要です。OAuthは事前登録方式です。チャット添付ファイルの自動取得は未実装です。**
プラグインにAIサービスのAPIキーを設定する必要はありません。普段使うAI側のアカウント等は別です。
開発用のブラウザープラグインやブラウザー拡張は、利用者の必須条件ではありません。
MCPに対応しないAIでは、従来のファイル受け渡し方式も使えます。

### 下書きのゴミ箱と復元

AIに「この下書きをゴミ箱に入れて」「ゴミ箱から復元して」と頼めます。
管理画面では下書き一覧のごみ箱アイコンから移動し、「ゴミ箱」表示の復元アイコンで戻せます。
操作できるのは下書きの所有者本人だけです。公開予約中は、先に予約を取り消してください。
保存履歴・ファイルは復元用に保持し、公開済みの記事・共通部品・WordPressのメディアは削除しません。
復元によって公開や予約が再開されることもありません。完全削除・自動消去は行わないため、使用容量は減りません。

## 2. インストール

1. テストサイトのWordPressとデータベースをバックアップする。
2. 管理者でログインし、「プラグイン」→「新規追加」→「プラグインのアップロード」を開く。
3. `atshift-deft-0.7.0.zip` を選択し、インストール・有効化する。
4. 左メニューの **atshift DEFT** を開く。
5. **Components** に初期部品の **Introduction** と **Article resources** が表示されることを確認する。

インストール用ZIPとSHA-256は [GitHub Release](https://github.com/at-shift/atshift-deft/releases/tag/v0.7.0) から取得します。GitHubの「Download ZIP」はソース一式で、インストール用ZIPとは別です。WordPress.org版は申請準備中で、配布開始は承認後です。
開発者はリポジトリで `npm run build:php-deps`、`npm run pack:wordpress` の順に実行すると `.local/releases/` に依存ライブラリ同梱ZIPとSHA-256を作成できます。
サーバーへNode.jsや別のAIサービスを設置する必要はありません。

宣言上の要件はWordPress 6.9以上、PHP 8.2以上、DOM・mbstring・OpenSSL・Sodium、InnoDBと名前付きロック対応のMySQL/MariaDBです。
PHP 8.2未満では処理開始前に停止し、管理者へ必要なPHPバージョンと現在のバージョンを警告します。保存済みデータは変更しません。予約投稿なども停止するため、更新前にサーバーのPHPを確認してください。
動作確認環境はWordPress 7.1、PHP 8.3.36、MySQL 8.4、Twenty Twenty-Fiveです。
宣言した最低バージョン、マルチサイト、ほかのテーマやホスティング環境はまだ検証していません。
外部から使うテストサイトはHTTPSを使用してください。HTTPの例外は専用の127.0.0.1ローカル環境だけです。

## 3. 担当者を設定する

利用者ごとに別のWordPressアカウントを使ってください。同じAIアカウントかどうかではなく、
ログイン中のWordPressアカウントが記事・ファイル・担当者用部品の所有者になります。

管理者が「ユーザー」で対象のテストユーザーを編集し、適切な権限グループを選択します。

| 権限グループ | 利用範囲 |
| --- | --- |
| atshift DEFT author | 本人の記事・ファイル・確認操作、限定的な共通構造の新規登録 |
| atshift DEFT publisher | authorの範囲に加え、本人の記事の即時公開・予約と公開接続キー発行 |
| atshift DEFT designer | authorの範囲に加え、共通部品の登録・変更・利用停止 |
| 管理者 | 共通部品管理と本人の作業。プラグイン経由で他人の非公開記事や部品には入れません |

designerには共通HTML/CSSを扱う信頼が必要です。通常の記事担当者全員に付ける必要はありません。
共通部品の新規登録と変更は内部では別権限ですが、designerロールは両方を持ちます。
プラグインは既存ユーザーの権限を自動変更しません。WordPressのロール変更は既存の権限にも影響するため、
まず専用テストユーザーで確認してください。組織の担当者交代・所有権移管はまだ実装していません。

## 4. 最初の記事を作る

最初に表示される案内で **AI用手順書をダウンロード** し、普段使うAIに渡してください。
案内はアカウント・サイトごとに初回のみ表示されます。ダウンロードボタンはその後も残ります。

### 最初の流れ

1. 手順書をAIへ添付するか、Chat projectフォルダーへ入れ、「この手順書を読んで、接続から案内して」と伝える。
2. AIが利用するアプリに合った接続手順を案内する。必要な設定・WordPressログイン・許可だけ、案内に沿って進める。パスワードや接続キーはチャットへ貼らない。
3. AIが実際のMCPツールで読み取り専用の接続確認を行う。手順書を渡したことやキーを作ったことだけでは、接続完了にはならない。
4. 接続後、AIが一度だけ「サンプルで試す／自分の記事を作る」を案内する。スキップしてよい。編集中の記事の再開には体験を挟まない。
5. 試す場合は、手順書に入っている架空の案内を、サンプルと分かる名前の別下書きへ保存し、プレビューする。別ファイルや実資料の準備は不要。公開・予約や実資料のアップロードは行わない手順とする。
6. 必要なら「もう少し短く」などの修正を試し、自分の記事へ進む。先に伝えた内容や資料は引き継ぎ、同じ説明をやり直さない。サンプルは非公開の下書きとして残る。

スキップした場合は、そのまま「誰に、何を伝えたいか」を相談します。既に伝えていれば、AIがその内容を使います。
プレビュー取得権限やAI側の表示機能がない場合は、本人のWordPressログインが必要なプレビュー画面で確認します。
これはAI向け手順の整備であり、プラグインがAIアプリの設定を自動操作する機能ではありません。
接続やサンプル体験への同意は、実際の記事の公開・予約への同意とは別です。

以下の接続方法は、AIの案内に沿って参照する詳細手順です。先にすべて覚える必要はありません。

### OAuthで接続する

1. 管理者が公式 **MCP Adapter 0.7.1以上** を有効化する。
2. **AI connections** でサービスを選び、**Register an application** にAIサービス側で表示される正確なcallback URLを登録する。必要な範囲だけ追加権限を許可する。
3. 担当者本人がAIサービスのMCP設定へ、画面のendpointとclient IDを入力する。認証方式はOAuth、client secretは空欄。PKCE S256対応のpublic clientが必要。
4. AI側からWordPressログインへ進み、自分の担当者アカウントで権限を確認して許可する。パスワードをAIチャットへ渡さない。
5. 同じAIとの会話へ戻り、接続確認を依頼する。読み取り専用の確認後、サンプル体験か記事作成へ進む。公開を許可する場合だけpublishing endpointと `sf:publish` を選ぶ。

接続先登録はサイト共通ですが、許可とデータは担当者別です。接続許可は最大30日、アクセストークンは10分で更新されます。**Revoke** で本人の接続を取り消せます。管理者の **Disable application** は全担当者の該当アプリと予約投稿に影響します。
この版は自動クライアント登録・client secret方式には未対応です。各サービスの実アカウントでの接続、ファイル転送・表示は別途確認が必要です。
ローカルサイトへクラウドAIは接続できません。OAuth discoveryの警告が出る場合は、表示されたmetadata URLをWordPressへ転送するサーバー設定が必要です。自動で公開トンネルは作りません。

### 接続キーで直接保存・再開する

1. 管理者が公式 **MCP Adapter 0.7.1以上** を別途インストール・有効化する。
2. 担当者本人で **atshift DEFT → AI connections** を開く。
3. **Your AI / client** で利用するアプリを選び、表示された接続条件を確認する。接続名を入力する。段組の補充・ファイル転送・持ち出しプレビューも任せる場合は **Allow reusable layouts, private file transfers and portable previews** を選び、**Create connection** でキーを作る。
4. AIアプリのMCP接続設定へ、表示されたURLと `Authorization: Bearer 接続キー` を設定する。
5. 同じAIとの会話へ戻り、接続確認を依頼する。AIが実際のcontext応答を確認してから、サンプル体験か記事作成へ進む。**Last connected** の表示だけでは、現在のAIの接続確認の代わりにはならない。
6. 続きを依頼すると、AIが保存済み下書きと版番号を読み、更新できる。

Streamable HTTPとAuthorizationヘッダー設定に対応するMCPクライアントが必要です。
OAuthクライアントには前項の別手順を使います。接続キーをclient IDやclient secretへ入れないでください。
キーは一度だけ表示し、30日で失効します。チャット本文には貼らず、AIアプリの安全な認証設定に保管してください。
取り消す場合は該当接続の **Revoke** を押します。下書きは消えません。WordPressのパスワードをAIへ渡す必要はありません。
通常のキーは本人の下書きの保存・再開と部品参照だけです。作成時に追加許可すると、限定構造の新規登録・ファイル転送・非公開プレビュー取得まで進められます。既存キーに権限は追加されません。共通部品の上書き・任意コードの登録・確認画面の承認操作は許可しません。公開接続は次項で別途許可します。
`127.0.0.1` / `localhost` は同じPC上のクライアント専用です。クラウドAIからは接続できません。

### AIサービス別の経路

| 利用先 | この版の状態 |
| --- | --- |
| ChatGPT | 事前登録型OAuthの経路を用意しています。実アカウントでの接続は別途検証します。 |
| Claude / Claude Desktopのリモート接続 | 事前登録型OAuth、または限定提供の個人専用Request headers。外部到達可能なHTTPSが必要です。 |
| Claude Code | 秘密を含まないHTTP接続設定をダウンロードできます。Claude Desktopの設定ファイルとは別です。 |
| GeminiのWeb・モバイルアプリ | 事前登録型OAuthの経路を用意。公式提供条件は米国・英語・18歳以上・個人アカウント等を要確認。日本で使えるとは扱いません。 |
| Gemini CLI | HTTP接続設定をダウンロードできます。Web版Geminiとは別の利用経路です。 |
| Codexデスクトップ版 | 専用の選択肢から、画面のURL・ヘッダー欄へ設定します。CLI / IDE用テンプレートとは別です。 |
| ローカルCodex CLI / IDE | 環境変数からキーを渡す設定をダウンロードできます。ChatGPTのWeb接続とは別です。 |
| その他 | HTTPと安全な認証ヘッダーに対応するMCPクライアント、または手動のJSON受け渡しです。 |

設定テンプレートにはキーを含めません。画面に表示された環境変数を、その担当者のクライアント起動環境へ安全に設定してください。
既存の設定ファイルを丸ごと置き換えず、該当エントリーを追加します。組織共有コネクターに個人のキーを登録すると全員が同じ担当者として動くため、使用しないでください。
**Authenticated request received** は認証通信の確認であり、そのサービスでの添付転送・プレビュー表示まで保証しません。
提供条件の確認日は2026-10-31です。詳細と公式資料は同梱の [CONNECTIONS.md](docs/CONNECTIONS.md) にあります。

### Claude.appの入口

2026-10-31に確認した画面では、**設定 → コネクタ → 追加** から **カスタムコネクタを追加** を開きます。最初の画面には「名前」「MCP サーバー URL」「続ける」があります。

次の認証画面に **リクエストヘッダー** がある場合、個人専用コネクターでは次の接続キー方式を使えます。

1. **サインインなし** を選びます。OAuthクライアントの指定は不要です。
2. **ヘッダーを追加** で、名前を `Authorization`、値を `Bearer <connection-key>` にします。`<connection-key>` は本人の接続キーに置き換え、`Bearer` の後ろに半角スペースを1つ入れます。必須の指定がある場合は有効にします。
3. **追加** 後、利用する会話でコネクターを有効にし、AIへ読み取り専用の接続確認を依頼します。

「サインインなし」はOAuthを使わない意味で、WordPress側のキー認証は残ります。名前・URL・チャットへキーを入れず、組織共有コネクターへ個人のキーを登録しないでください。リクエストヘッダーがないアカウントでは、この方法を使わず、OAuthなど別の経路を確認します。Claude Codeの設定ファイル手順とは別です。

2026-10-31の確認では、Xserver側のアクセス制限を解消した後、利用者からClaude.appでの接続と、サンプル記事の作成・下書き保存ができたとの報告がありました。完了したのは下書きまでで、公開はしていません。これは1つの環境での利用者による確認結果です。context応答・保存内容の再取得の独立した照合、プレビュー・ファイル転送・公開、別経路のOAuth接続は引き続き未検証です。

### クラウドAIだけ接続できない場合

Claude.appのリモートコネクターも、MacではなくAnthropicのサーバーから接続します。手元のCodexなどで接続できても、クラウド側の通信が許可されているとは限りません。

403や接続エラーの場合は、キーを作り直す前に、失敗時刻のホスティング・WAFログとアクセス制限を確認します。キーなしでDEFTへアクセスした際の401は正常な認証要求です。403の原因は表示だけでは断定できません。

Xserverでは **WordPressセキュリティ設定 → 対象ドメイン → 国外アクセス制限 → REST APIアクセス制限** が確認箇所です。ドメイン単位の設定は、DEFT以外のサイトにも影響する可能性があります。管理者と、公式の最新送信元IPを使った許可リストなど必要最小限の例外を検討し、変更前に範囲と承認を確認してください。国外制限・WAF・ログイン保護・DEFT認証を一括で無効化する案内ではありません。

承認した調整後に再接続し、実際のAI会話からcontextを取得してからサンプルへ進みます。プラグインがサーバー設定を自動変更することはありません。詳しい切り分けと公式資料は [Cloud Connection Errors](docs/CONNECTIONS.md#cloud-connection-errors) を参照してください。

### Codexデスクトップ版の入口

2026-10-31に確認した画面では、**設定 → プラグイン → 追加 → MCPサーバーを追加** から登録します。
名前を付け、タイプを **ストリーミング可能なHTTP** にして、DEFTのMCP endpointをURL欄へ入力します。**STDIOではありません。**

このヘッダー方式では **Bearer トークン環境変数は空欄** にします。**ヘッダー** の左欄は `Authorization`、右欄は `Bearer ` に接続キーを続けた値です。`Bearer` の後ろには半角スペースを1つ入れます。キーをチャットやスクリーンショットへ含めないでください。

保存後の編集は、プラグイン内の **MCPタブ → 自分で付けたサーバー名の歯車** から行います。該当サーバーを有効にし、元の会話で読み取り専用の接続確認を依頼してください。ツールが出ない場合は、再起動の操作が表示されていれば使い、なければアプリを再起動して会話を再開します。保存や有効化の表示だけでは接続完了とはしません。

### ChatGPT Web版の入口

2026-10-31に確認した画面では、**設定 → プラグイン → エージェント一覧を見る → 追加 → カスタムMCPサーバーを追加** です。設定内のインストール済み一覧ではなく、「エージェント一覧を見る」で移動した先に追加メニューがあります。

通常のChatとWorkにはプラグインの利用経路がありますが、利用可否にはアカウントや組織の制限が適用されます。DEFTでは前述のOAuth接続を使い、Codex用の固定キーや「認証なし」で代用しません。作成したプラグインをインストールし、利用する会話で選択して実際の接続を確認します。今回確認できたのはWeb版の追加メニューまでで、DEFTのOAuth接続・記事作成は実機未検証です。

画面名が異なる場合は、利用しているアプリと表示内容を確認してから進めます。どの環境にも「設定 → MCP」があるとは案内しません。

### 普段の記事作成

1. 誰に何を伝えたいかをAIに話し、資料を渡す。段組の見本画像は任意で、お任せでも構いません。
2. AIが既存部品を優先してページ案を作ります。不足時だけ、許可された限定構造を新規登録します。
3. 必要な画像・PDFだけを非公開で転送し、本文へ組み込みます。参考資料を渡しただけでは、その資料をサイトに掲載しません。
4. AIが保存版のHTMLプレビューを取得します。対応するAIでは非公開アーティファクトとして表示し、非対応ならHTMLファイルまたはWordPressの確認リンクを使います。
5. 会話で修正し、公開する場合は「今すぐ公開」「○月○日○時、日本時間で予約」と伝えます。公開を指示しなければ下書きのままです。

持ち出しプレビューは段組・本文の確認用で、サイトのテーマやJavaScriptは含みません。
画像は合計2 MiBまで埋め込み、超過画像・未固定画像・PDF本体は省略理由をAIへ返します。
テーマを含む最終表示は本人のWordPressプレビューで確認してください。公開プレビューURLは発行しません。
AIが添付ファイルの実体を読み出しHTTP転送できる必要があります。チャットへの添付だけでは自動転送されません。
Word・テキストなどはAIが記事の資料として読み、サイトへ送るファイルはJPEG・PNG・WebP・PDFに限定します。

### デザイン・段組も会話で相談する

文章だけでなく、ページ全体の構成や段組もAIに作ってもらえます。見出し・画像・本文の配置、セクションの順番、縦積みと左右2列の組み合わせ、対応するQ&A表示などを相談できます。希望を言葉で伝えるだけでも、参考画像を見せても構いません。コードや参考画像の準備は必須ではありません。

- **今のテーマのデザインを活かす**：「サイトの雰囲気に馴染ませたい」と伝えます。AIは登録済みの部品から適したものを選び、部品で上書きしていない部分にはテーマのスタイルが適用されます。テーマ固有のデザイン要素は、対応する部品がある範囲で利用します。
- **記事用に別のレイアウトを組む**：「画像と本文を左右2列にして、その下に開催情報をまとめたい」などと伝えます。既存部品を優先し、不足があって権限もある場合は、縦配置・2列・Q&Aの対応構造を追加できます。対応する2列構造は狭い画面では縦に並びます。

迷う場合はAIに提案を任せられます。参考画像は構造や配置の参考で、完全再現を保証するものではありません。MCPからテーマのスタイル一覧が渡るわけではなく、テーマ設定も自動変更しません。別のレイアウトもサイト上ではテーマの影響を受けるため、どちらも本人のWordPressプレビューで確認してください。

構築権限のあるAIに「締切を背景色で強調して、申込リンクをボタンに。テーマは変更せず再利用できる部品にして」と頼めます。AIは装飾済みの共通部品を優先し、足りない場合だけ色・余白・枠線・文字・段組比率などの対応設定で新規登録します。装飾はDEFTの部品と記事に保存され、持ち出しプレビューや公開にも引き継がれます。テーマの追加CSSは変更せず、保存済みの他の記事にも変更を波及させません。対応範囲外のCSSや独自マークアップの変更は、別途デザイナー・管理者による対応が必要です。

### AIに公開日時を設定してもらう

**「下書きを保存」やReviewの承認だけでは公開されません。** AIに公開を依頼する方式です。
記事画面とAI接続画面の **「公開・予約の手順」** から、必要な設定を確認できます。

1. 下書きを所有するWordPressアカウントで進めます。管理者は公開権限を持っています。その他の担当者は **atshift DEFT publisher** が必要です。公開の選択肢がなければ管理者へ相談してください。別のアカウントに切り替えたり、他人のキーを使ったりしません。
2. 初回のみ **atshift DEFT → AI connections** で利用するAIを選びます。キー方式では **Allow immediate and scheduled public publication of my drafts**（自分の下書きの即時公開・予約公開を許可）を選び、**Create connection** で新しいキーを発行します。
3. 発行された公開用URLと新しいキーを、AI側に別の接続として追加します。下書き用の接続は残します。以前のキーの権限は変わらず、URLだけの変更でも公開できません。キーは接続設定に入力し、チャットには貼りません。OAuth方式では、管理者が公開アクセスを許可した登録済みアプリを選び、**Use the publishing endpoint** と本人のWordPress同意画面で `sf:publish` を許可します。
4. 同じAIとの会話へ戻り、読み取り専用で公開権限の接続確認を依頼します。保存済み記事を確認して、「この下書きを今すぐ公開して。公開URLも教えて」または「11月5日午前9時、日本時間で公開して」のように希望を伝えます。接続設定が終わっただけでは公開の依頼になりません。
5. AIが不足する日時・タイムゾーンを質問し、最新保存版を指定して公開・予約を設定する。下記の投稿先対応版では、この記事の投稿先が未指定の場合に「どこに投稿しますか？」も確認します。
6. AIの結果と **Articles** の **Publication** 状態を確認します。公開後は **View published post** から公開ページを開けます。予約済みはまだ公開されていません。予約取消はAIまたは **Cancel reservation** から行います。

このキーは追加のWordPress承認なしに公開できる強い権限です。会話で希望を聞くようAIへ指示しますが、
サーバーが実際の人の発言を証明する仕組みではありません。信頼する接続先だけに許可してください。
予約後に本文・素材・動作方針が変わると停止するため、内容を確認してAIへ予約の再設定を依頼します。
**Revoke** は未実行予約を取り消します。30日のキー失効は新規操作だけを止め、すでに指定した予約は継続します。
実行に入った公開処理は完了することがあります。公開済み記事はRevokeでは非公開になりません。

### 記事ごとに投稿先を選ぶ（開発中）

0.7.0では、作った記事を「通常の投稿」「固定ページ」「利用できる既存のカスタム投稿タイプ」のどこに公開するか選べます。「これは固定ページに」「これはイベントに掲載して」のように、普段の会話で指定できます。
未指定ならAIが **「この記事はどこに投稿しますか？」** と、利用できる投稿先を示して確認し、返答を待ってから公開・予約に進みます。選択肢が1つでも、その投稿先でよいか確認します。
この記事の投稿先をすでに伝えている場合は聞き直さず、投稿先と公開日時を明示します。別の記事の選択を勝手に引き継ぐことはなく、投稿先を選んだだけでも公開しません。
固定ページ・カスタム投稿には、DEFTの公開権限に加えて、その投稿タイプの作成・公開権限が必要です。
投稿先が見つからない場合や名前が曖昧な場合は確認し、通常投稿へ勝手に振り替えません。
親ページ・テンプレートの選択、専用カスタムフィールドの入力はまだ対象外です。プレビューはDEFT本文の確認用で、投稿先専用テンプレートの完全な再現ではありません。

### カテゴリー・タグを選ぶ（開発中）

投稿先を決めたら、「カテゴリーはお知らせに」「読書会のタグを付けて」のように既存の分類を指定できます。指定がなければ、AIが候補を少数に絞り、投稿先・日時と合わせて確認します。希望がない場合はWordPressの既定の分類になることを案内します。通常の投稿では、カテゴリーを指定しなければサイトの既定カテゴリーが付きます。
AIは投稿先で使える分類を確認するため、カテゴリーのない固定ページに無理に付けることはありません。公開用の独自分類にも対応しますが、新しいカテゴリー・タグ・分類の自動作成は行いません。
分類の割り当てにはWordPress側の権限が必要です。DEFT publisher権限だけでは追加されないため、選べない場合は管理者に相談してください。
選択した分類は **Articles → Publication** に表示されます。予約後に項目の削除・改名・親階層の変更、投稿先からの分類解除、権限の喪失があれば公開を停止し、最新の選択を確認して再予約します。公開ページには最小限のJSON-LDと、本文HTMLから作る公開構造JSONへのリンクも出力します。下書き・内部設定・認証情報は含めず、非公開に戻すと取得できなくなります。会員限定・有料記事の制御プラグインを併用する場合は、公開構造JSONの無効化またはアクセス制御との連携が必要です。CSSで隠すだけでは非公開になりません。詳しくはGitHubの `docs/PUBLIC-STRUCTURE.md` を参照してください。

予約はプラグイン内で待機し、期限到来時に指定した公開先の投稿を作ります。投稿一覧には実行後に現れます。古いAPIから投稿先を省略した場合は互換性のため通常の「投稿」になりますが、AIがこの既定値を理由に確認を省くことはしません。
投稿先の無効化や権限の喪失があると予約を停止します。下書き自体の保管先はDEFT専用のままで、公開先の指定は公開・予約の設定に記録されます。
WordPressのWP-Cronはアクセスが少ないと遅れるため、時刻重視のサイトではサーバー側の定期実行を設定してください。
公開済み投稿の更新はまだ対象外で、その後の **Save draft** は公開内容を変更しません。

DEFTのメニューはWordPressの **Settings（設定）** の下にあります。下書き一覧には、所有者名とWordPressの権限グループが表示されます。

公開または予約が確定すると、DEFTの下書き一覧から外れ、選択した投稿先の一覧で確認できます。予約記事は非公開の **Scheduled (DEFT)（予約済み・DEFT）** として表示され、公開時刻にDEFTが権限と内容を再確認してから公開します。本文・添付ファイル・保存履歴は削除しません。予約の変更・取消は一覧の **Manage reservation in DEFT（DEFTで予約を管理）** またはAIへの依頼で行います。取消・内容変更による無効化・公開失敗時は、DEFTの下書き一覧に戻ります。AIは公開用接続の `list-publications` で予約・公開済み記事を探せます。

投稿先のWordPress一覧を開くには、その投稿タイプの一覧閲覧権限が必要です。DEFTが権限を自動追加することはありません。更新前に作った予約で投稿先の記事がまだない場合は、再予約または公開実行までDEFTに残ります。
画像・PDFは公開時に固定した非公開コピーから配信し、通常メディアライブラリへの自動登録はまだ行いません。
プラグインを無効化すると予約処理・その素材配信・スタイルは止まります。削除・保管期間のUIも未実装です。

### 手動で試す場合

必要な場合だけ、WordPress画面で保存とプレビューを試せます。AI接続の必須条件ではありません。

1. 担当者でログインし、**atshift DEFT → Articles** を開く。
2. **New article** を押し、**Title** に記事名を入力する。
3. **Component** で **Introduction** を選び、横の「+」を押す。
4. **Heading** と **Body** を入力し、**Save draft** を押す。
5. 下のプレビュー、または **Open theme preview** で表示を確認する。
6. 再読み込みして一覧から同じ記事を選び、内容が残っていることを確認する。

下書きは一般の「投稿」とは別管理です。保存してもサイトには公開されません。
編集したいときは **Edit article** を開きます。部品の上下移動・削除・表示方式もここで変更できます。
必須欄の不足や古い版からの更新は保存時に拒否されます。表示された理由を直してから保存してください。

## 5. 普段使うAIに記事作成を依頼する

### AIへ渡す

新しく始める場合は、最初の **Articles** 画面にある **AI用手順書をダウンロード / Download AI guide** を押します。
`atshift-deft-ai-guide.md` を普段使うAIに読ませて、接続から案内してもらいます。既に読ませて接続できている場合は、この作業を繰り返しません。
この1ファイルに接続案内、任意の練習用のお題、AI向けルール、共有部品の入力項目・表示方式、設定Schema、新規記事用テンプレートが入っています。
記事を先に作成する必要はありません。私有部品、記事本文、メディアファイル、利用履歴、認証情報は含みません。
共有部品のラベルや説明は含まれるため、依頼先AIへ渡せるサイト設定であることを確認してください。

案内は利用者ごと・サイトごとに初回アクセスだけ表示され、手順書のダウンロードボタンはその後も残ります。
初回かどうかはWordPressに保存するため、同じアカウントなら別のブラウザーでも繰り返し表示しません。

保存済み記事の続きを依頼する場合:

1. 編集する保存済み記事を一覧から選ぶ。
2. **Article handoff** を押して `atshift-deft-ai-handoff.json` をダウンロードする。
3. 普段使うAIの会話に、このJSONと修正したい内容を渡す。

依頼文の例:

> この手順書の指示とSchemaに従って、初めて来場する人向けの見学案内を組み立ててください。
> 既存部品を優先し、表示方法を選んだ理由を日本語で短く説明してください。
> 記事本文も日本語です。確認できない日時・料金は作らず、必要な点だけ質問してください。
> 完成案は composeTemplate を基に、article と expectedVersion だけを持つJSONファイルで返してください。
> 接続していないWordPressへ保存済みとは言わないでください。

JSONには本人の記事本文や部品の説明が含まれます。依頼先AIへ渡してよい情報か確認してください。
パスワード・REST nonce・プレビュー用認証URLは、この受け渡しに必要ありません。
ダウンロードしたJSON自体はAPIへログインできる鍵ではありません。

### AIの結果を取り込む

1. AIが返した記事JSONを受け取る。管理画面で **Import snapshot** を押し、そのファイルを選ぶ。
2. 未保存の候補として読み込まれたことを確認する。
3. **Save draft** を押し、実テーマのプレビューを確認する。
4. 修正をAIへ頼むときは、保存後に **Article handoff** を取り直す。

AIに渡してから記事を手動変更した場合、古いJSONは取り込めません。新しい受け渡しJSONで作り直します。
読み込むだけでは保存されません。現在はプレビュー前に非公開下書きへ保存する流れです。
認証済みのブラウザーを操作できるAIなら、その許可された範囲で同じ操作を代行できますが、
このプラグインが自動でAIとの接続やブラウザー操作権限を設定するわけではありません。

## 6. 全体カタログから部品を使う

「自分が作った部品」だけに限定しません。AIは次の順で探します。

1. **Used by me**: 自分が記事で利用した部品。
2. **Shared catalog**: サイト全体の共通部品。
3. どちらにも足りない場合だけ、新しい共通構造。

自分の利用リストになくても、有効な共通部品ならそのまま使えます。
担当者用に複製せず、同じ部品IDと版を参照します。記事を保存すると利用リストへ自動記録されるので、
「自分に追加しますか？」という確認操作はありません。他人の利用リスト・記事・素材は見えません。
以前からある記事は次に内容を変更して保存したときに記録されます。過去記事の一括走査・書き換えはしません。

AIには **AI handoff** の `usedComponents` と `sharedComponents` が渡ります。
通常は利用者がカタログを操作する必要はなく、記事の依頼とプレビュー確認を中心に進めます。
手動確認では **Components → Scope** または記事編集の部品選択欄を使えます。

### 全体にも必要な構造がない場合

1. **Components** の **AI handoff** をAIへ渡し、不足する用途を伝える。
2. AIに `schemas.structure` に合う `recipe`・`expectedVersion`・`reuse` のJSONを用意してもらう。
3. `reuse` には確認済みの部品ID・版、catalogToken、不足する理由を含める。
4. **Import component** で取り込み、**Register version** で共通構造として登録する。
5. 登録結果のID・版で記事を組み立てる。**AI handoff** を取り直せば結果を含む現在のカタログが渡る。

同じ構造が既にある場合、登録結果はその部品を返します。新しいコピーは作られません。
AIは要求した新規IDではなく、返されたID・版を使います。別担当者が同時に同じ構造を作る場合も同様です。
意味の似た部品を完全に判定する仕組みではなく、項目キー・型・構造・CSS等の正規化一致で判定します。

手動確認には **New structure** のQ&A見本を使えます。フィールド定義に入力値はありません。
`value`・`alt`・`assetRef` や画像URLは部品ではなく、本人の記事の入力値へ入れます。
部品名・項目名・用途説明は全担当者に見える設定なので、固有の案件情報・秘密・個人情報を入れないでください。
システムが任意の説明文から秘密情報を自動判別するわけではありません。

対応する構造は **stack（縦配置）・columns（2列、狭い画面では1列）・qa**。
項目はtext、textarea、image、linkで、1部品12項目までです。任意のHTML/CSS/JavaScript、
独自クラス、入れ子の繰り返し、送信フォームは指定できません。
共通構造の必須欄は登録時には空ですが、記事保存時には必須入力として検証されます。

Q&Aはquestion（text）とanswer（textarea）です。同じ部品を繰り返し使い、
**Visible answer** または **Expandable answer** を選びます。重要な注意事項は開閉の中に隠さないでください。

サイト全体100部品、各部品30保存版が上限です。利用停止も件数に含み、自動削除はしません。
共有部品の新規作成は担当者ごとに標準20件です。既存共有部品の再利用は枠を消費せず、
管理者が後から編集しても作成者の計上先は変わりません。上限を超えた既存データも削除しません。
既存の共通部品を変更・利用停止できるのは管理権限を持つ人だけです。
記事は使用した版を保持し、部品更新で勝手に変わりません。旧版を使った履歴だけでは、
新しい記事へ停止中・旧版の部品を持ち込むことはできません。

## 7. 既存の本人用部品と個別の機能

alpha.7までの本人用部品は自動共有しません。**My private components** から引き続き利用できます。
**New personal component** と従来APIは個別用途・互換性のために残しますが、通常の新規作成は
前項の共通構造を使ってください。本人用の上限は停止中を含め20部品です。

従来の **Register shared copy** は、共通登録権限を持つ本人が明示的に操作する例外経路です。
定義だけでなく見本内容も共有されるため、確認画面を読み、機密情報がないことを確かめます。
原本と既存記事は残ります。他人の本人用部品を管理者が勝手に共有することはできません。
この操作はa8の通常の構造登録・再利用には不要です。

### JavaScriptが必要な機能

alpha.9ではHTML、CSS、必要な場合だけJSの順に選びます。Q&A開閉はHTML標準機能、表示アニメーションはCSS、画像拡大は同梱JSで動きます。端末の「動きを減らす」設定ではCSSアニメーションを止めます。
1. **Components > Behaviors** で利用可能な動作を確認します。AI handoffにも同じ一覧と設定Schemaが入ります。
2. AIに部品の `behaviors` へ動作ID・正確な版・対象項目キー・設定を付けてもらい、通常の部品登録で保存します。画像拡大の対象はimage項目、表示アニメーションの対象はrootです。
3. 記事の **Edit article > Behaviors** で有効・無効、表示時間、キャプション表示を手動調整できます。AIは `behaviorSettings` で同じ設定を指定できます。
4. サイト全体で止める場合は、管理者が **Components > Behaviors** のチェックを外します。次回プレビュー読み込みから停止し、本文や画像は残ります。すでに開いているタブは再読み込みしてください。
動作を含む記事はv3形式で保存し、既存v1/v2記事は自動変換しません。停止・再有効化後はv3記事の以前の承認を無効にして再確認を求めます。任意のJSファイルや外部スクリプトの登録はできません。
新しい実行コードの追加は通常の部品選択とは別に検証・承認する必要があります。
現時点でAIが任意のJSを挿入したり、動かないフォームを動作済みと説明したりしないようにしてください。

## 8. 言語の扱い

管理画面が英語でも、AIの提案・確認・エラー説明は利用者の言語で返すよう指示します。
本人の指定、現在の会話、WordPressユーザーの言語設定の順で扱い、国だけでは決めません。
**Components → Reply language** は `ja`、`en-US`、`pt-BR` 等を指定する明示的な設定欄です。
記事用handoffのユーザーロケールは補助情報なので、会話では別の希望言語を指定できます。
記事本文を英語、説明を日本語にする依頼も可能です。ID・項目キーは翻訳しません。
AIが必ず指示に従う保証や、管理画面全体の自動翻訳機能ではありません。

## 9. 画像・PDFを使う

ファイルを使わない最初の試用では、この設定は後回しにできます。
非公開ファイルを使う前に、サーバー管理担当者が公開領域の外に専用ディレクトリーを用意します。
下記は例です。実際のホストの絶対パスに置き換えて `wp-config.php` に設定します。

```php
define( 'SF_PRIVATE_MEDIA_DIR', '/srv/private/structured-fields' );
define( 'SF_PUBLIC_DOCUMENT_ROOT', '/srv/www/example/public' );
```

Webサーバーの別名公開・別サイト・CDN等からも見えないことを管理担当者が確認してください。
PHP fileinfoとUnix権限が必要で、専用の子ディレクトリーは0700、ファイルは0600になります。
シンボリックリンクや不明な公開範囲は拒否し、通常のuploadsへ自動で逃がしません。
設定ファイル編集前にもバックアップを取得してください。WindowsのACL環境は未対応です。

1. 本人の記事を保存し、**Private files** を開く。
2. 参考資料は **Reference only**、記事に載せる候補は **Publication candidate** を選ぶ。
3. **Add files** でJPEG・PNG・WebP・PDFを追加する。
4. 画像またはリンク項目を持つ部品を追加し、**Article media** でファイルと代替文・リンク文言を選ぶ。
5. 記事を保存してプレビューする。

参考用ファイルは記事へ紐付けできません。公開候補もまだ非公開です。
既存のWordPressメディアは本人がアップロードした対応ファイルだけ検索・再利用できます。
**通常のWordPressメディアURLが非公開になるわけではありません。** 元のメディアは複製・変更しません。
ファイルが消失・変更した場合は、別の内容へ差し替えずプレビューを拒否します。
標準上限は1ファイル10MiBまたはホスト上限の低い方です。1記事50ファイル/100MiB、サイト全体500MiBです。
加えて、非公開ファイルは担当者ごとに記事をまたいで標準100MiBです。参考用・公開候補の両方を含み、
転送キー経由でも発行した担当者に計上します。同じ記事・用途・内容の再送は二重計上しません。
担当者別上限はサーバー側のWordPressフィルターで調整できます。運用者向けの詳細は開発リポジトリの `docs/ALPHA12.md` を参照してください。
ウイルス検査やPDFの無害化を完了したという意味ではありません。

## 10. 確認と終了

保存済み記事の **Review** から、その版と使用ファイルを確認できます。
承認・修正依頼・承認取消はアカウントの判断記録です。承認しても公開されません。
本文や使用ファイルが変わると以前の承認は無効になります。
未固定の画像URLやCSS外部画像がある場合、この厳密なファイル確認は利用できません。

作業を再開するときは、同じWordPressアカウントで保存済み記事を選びます。
無効化してもデータは残ります。削除・保管期間・担当者引き継ぎの仕組みは未実装です。
更新前にはDB・プラグイン・非公開ファイルのバックアップを揃えてください。
古いZIPに戻すだけで新しい形式のデータも戻るとは限りません。検証環境ごと復元できる準備が必要です。

## 困ったとき

| 表示・状況 | 対応 |
| --- | --- |
| メニューがない | WordPressの担当者ロールを確認する |
| 他の担当者の記事が見えない | 仕様です。共有ログインへ変更して回避しない |
| Catalog changed / sf_catalog_stale | 現在の部品を確認し、handoffを取り直す |
| sf_reuse_component | 指定された既存部品を使う。自分の停止中部品ならMy componentsで確認する |
| sf_component_quota | 新規作成を止め、既存部品の再利用・改訂を検討する。自動削除はされない |
| sf_shared_component_quota | 既存共有部品を再利用するか、管理者に担当者別の新規作成枠の調整を依頼する |
| sf_asset_user_quota | 既存ファイルを再利用するか、管理者に担当者別容量の調整を依頼する。自動削除はされない |
| Article changed | 記事を再読込し、新しい保存版をAIへ渡す |
| Private storage unavailable | 公開領域外の保存先・定数・権限をサーバー担当者に確認する |
| APIの401/403 | アカウント、必要な権限、ログイン期限・nonceを確認する。認証を無効化しない |
| 手元では接続できるが、クラウドAIでは403・接続エラーになる | ホスティング・WAFログと国外REST API制限を確認する。保護を一括解除せず、管理者と許可範囲を検討する。詳しくは [Cloud Connection Errors](docs/CONNECTIONS.md#cloud-connection-errors) |
| 画像が見えない | ファイルの所有者、用途、ハッシュ、ログイン、外部画像制限を確認する |
| 公開ボタンがない | 公開専用キーを設定したAIに、即時公開または希望日時を伝える |
| Publication: invalidated / blocked | 最新の記事・素材・権限を確認し、AIに予約を再設定してもらう |
| Publication: overdue | WP-Cronの実行をサーバー担当者に確認する |

開発用のローカル例: `http://127.0.0.1:8128/wp-admin/admin.php?page=structured-fields`
`http://127.0.0.1:5178/` は以前のブラウザー試作で、WordPressへ自動同期しません。
